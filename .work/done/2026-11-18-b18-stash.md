# b18 stash: destructive-guard allows a literal-ref stash drop

## Goal
BACKLOG: the guard refused a tagged `git stash drop` the agent passed by variable. Let a drop of one literal stash pass; keep the unsafe forms refused.

## Design (L012, written before coding)
The guard sees only the command text, never the stash message, so a message-tag rule cannot be checked. The mechanical rule: a drop is allowed only when it names exactly one literal stash.
Refuse:
- `git stash clear`
- bare `git stash drop` (drops the newest stash)
- `git stash drop $REF`, `$(...)`, any non-literal word (variable, substitution, short sha, range)
- `git stash drop stash@{0} stash@{1}` (more than one ref)
Allow:
- `git stash drop stash@{N}`
- `git stash drop <40-hex sha>`
- `-q`/`--quiet` alongside exactly one such ref
Why: the caller must resolve and print the ref (git stash list --format) before dropping, so the drop is of a stash it identified; a variable the guard cannot expand stays refused.

## Acceptance criteria
- refusing and allowing case per form: tests/template/test_destructive_guard.sh (blocked: var, substitution, short sha, two refs, bare drop, clear; allowed: literal ref, literal sha), both shells.
- The old test `git stash drop stash@{0} is blocked` was replaced by the allow case: intentional contract change from the BACKLOG row, not a weakening.

## Open risks
- Real git rejects a bare sha for `stash drop` unless it is a stash reference; allowed per brief since the guard cannot tell.
- docs/rules/destructive-actions.md does not mention stash; left unchanged.
- Found by the test run: the guard splits segments on braces, so stash@{N} reached check_stash_drop as "stash@". Fixed by rewriting stash@{N} to stash@#N in check_text before the split. First run: 1677 passed, 2 failed (the allow case, both shells); after: PASS.
